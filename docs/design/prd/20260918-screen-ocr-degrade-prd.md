# PRD: 屏幕感知 OCR 降级方案（无障碍不可用时）

| 文档版本 | 创建日期 | 状态 | 作者 |
| :--- | :--- | :--- | :--- |
| v1.0.0 | 2026-09-18 | 已确认，待实施 | Bonio 团队 |

> 关联设计：`docs/design/arch/20260918-screen-ocr-degrade-arch.md`
> 背景事件：Android 13+「受限设置」导致 ADB 安装应用的 Bonio 无障碍服务虽已启用，但读取不到任何窗口内容（root 节点 `childCount=0`），Magic Cue 被迫走纯视觉模式，建议质量差且耗时超 30s 触发"分析超时"。

---

## 1. 需求背景与痛点

Bonio 的屏幕感知（Magic Cue / 伴随记忆 / `screen.context` 工具）依赖 **无障碍（Accessibility）树** 读取当前屏幕文本。但无障碍树存在以下不可控的失效场景：

| 场景 | 现象 | 影响 |
|------|------|------|
| Android 13+「受限设置」 | ADB 安装的应用即使开启无障碍，系统仍禁止读取窗口内容 | 文本捕获恒为空 |
| 用户未授予无障碍权限 | 服务未启用 | 同上 |
| 目标 App 的无障碍树受限/延迟 | 部分窗口返回空树或仅有标题 | 文本不完整 |

失效时 Magic Cue 只能依赖**纯视觉模式**（截图直接给云端大模型）：
- 视觉模式耗时长（20-40s），Magic Cue 客户端 30s 超时直接失败（"分析超时了"）；
- 纯截图理解对长文本（聊天记录、账单）质量不稳定，且截图全量上传有隐私顾虑。

## 2. 目标

1. 无障碍树不可用时，**本地 OCR** 从截图提取文本与 bbox 坐标，还原出与无障碍树**相同形状**的屏幕上下文，下游消费者零改动。
2. Magic Cue 在降级后回到**文本模式**（快、准、省流量），消除"分析超时"。
3. OCR 全程本地推理，**图像不出设备**，仅识别后的文本进入云端大模型。

## 3. 非目标（Non-Goals）

- 不替代无障碍主路径：无障碍可用时仍优先使用（文本结构化程度更高、含 viewId/可点击信息）。
- 不改变 Magic Cue 的产品交互（双击触发、气泡展示、点击注入）。
- 不实现基于 bbox 的自动点击（坐标仅持久化在 `nodes` 中为后续 cue 注入/自动化预留）。

## 4. 功能需求

### 4.1 降级链路
1. `screen.context` 请求进入后，先走现有无障碍路径；
2. 当无障碍文本内容为空（`content_len == 0`）时，自动触发降级：
   - 通过无障碍静默截图（现有 `takeScreenshot`，1080px）；
   - 本地 OCR 识别出文本行 + bbox；
   - 合成与无障碍路径**相同 schema** 的 payload 返回，`source` 字段标记为 `"ocr"`。
3. OCR 失败、超时（5s）或识别结果为空时，保持现有空结果行为（上层已有视觉兜底）。

### 4.2 输出契约（与无障碍路径一致）
- `content`：行文本按 **top → left** 排序、去重后拼接，遵循 `maxTextLength` 截断，**不携带坐标**；
- `nodes`：每行 `{text, bounds: "l,t,r,b"}`（与无障碍节点 bounds 格式一致）；
- `source`：`"ocr"`（无障碍路径为 `"accessibility"`），用于调试与统计；
- `package` / `title` / `truncated` 语义不变。

### 4.3 OCR 引擎
- 采用 **ML Kit Text Recognition v2（bundled 中文模型）**；
- 纯端侧推理，无 GMS 依赖（华为/三星均可运行）；
- 中文 UI 文本识别质量与桌面端 RapidOCR (PP-OCRv4) 同级。

### 4.4 性能要求
- OCR 单次识别 ≤ 500ms（1080px 截图，中端机）；整体降级链路（截图+OCR）≤ 1.5s；
- 首次调用允许模型加载预热（≤ 2s）；
- 无障碍路径可用时**零额外开销**（不截图、不 OCR）。

## 5. 用户可感知的变化

| 场景 | 现状 | 上线后 |
|------|------|--------|
| 微信双击 Magic Cue（受限设置下） | 纯视觉模式，30s 超时或空建议 | OCR 提取聊天文本 → 文本模式出建议，秒级返回 |
| 伴随记忆（双击记一记） | 屏幕文本为空，记忆内容贫瘠 | OCR 文本入库，可被 chat 检索 |
| LLM `screen.context` 工具 | 空文本 → 需截图视觉分析 | 直接拿到文本，省 token 省时间 |

## 6. 验收标准

1. 在"受限设置"未解锁的设备（MLN-L29，Android 16）上：微信界面双击，日志出现 `source=ocr`、`content_len>0`，Magic Cue 返回基于文本的建议；
2. 无障碍正常的应用：日志仍为 `source=accessibility`，行为与现状完全一致；
3. 关闭无障碍服务 + OCR 也失败：行为回退到现有视觉兜底，无崩溃；
4. OCR 延迟 P95 ≤ 1.5s（截图+识别）；
5. `nodes` 中每行携带合法 bounds，`content` 不包含坐标文本。

## 7. 风险与取舍

| 风险 | 应对 |
|------|------|
| APK 体积 +~25MB（中文模型内置） | 已确认接受；相比回退视觉模式省下的 token/时延成本值得 |
| 暗色模式/艺术字识别精度下降 | 文本模式 + 视觉模式可并行兜底（后续可做置信度融合） |
| 部分厂商截图 API 受限 | 复用现有 `takeScreenshot` 链路（无障碍截图已验证可用），失败则维持现状 |
| 隐私 | OCR 本地执行，仅文本上云（优于现状的截图上云） |
