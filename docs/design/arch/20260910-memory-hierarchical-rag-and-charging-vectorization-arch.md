## 1. 背景与核心问题

### 1.1 场景案例：微信询问“手机是否欠费”
用户在微信聊天中提出问题：*“手机是否欠费？”*。系统短信数据库中实际包含最新运营商通知：
> `【中国电信】账单提醒：尊敬的客户，您本账单周期为8月1日-8月31日，号码为181****6046等，账单合计121.36元（赠费抵扣0.00元，实际应付121.36元）。详情请点击 https://a.189.cn/vMeYnA 。`

但用户双击 Bonio 悬浮球后，Avatar 头顶显示“当前页面没有什么可以帮你”，未能给出任何有效回复胶囊。

### 1.2 根因排查
1. **端侧数据源断层**：
   - 现有的 `MagicCueController` Prompt 仅硬编码声明了 `contacts.search`、`calendar.events`、`memo_list` 3 个工具，缺乏查询短信（SMS）的工具能力；
   - 胶囊格式白名单仅限制在 `['contact', 'calendar', 'memo']`，对于账单（`bill`）或通用文本（`text`）类型无法接纳。
2. **时序与提问模式局限**：
   - Prompt 原先规则针对“他人向用户索要联系方式/日程”，对于用户自己提出的状态类提问（如“手机是否欠费”、“还剩多少流量”）缺乏匹配逻辑。
3. **端侧数据无法简单全量喂给大模型**：
   - 手机本地积累了海量短信、通话记录、联系人、日程、历史聊天记录与屏幕记忆，全部打包塞入 Context 会导致：
     - **超出上下文窗口**；
     - **巨大的 Token 成本与网络流量**；
     - **严重的隐私泄漏风险**（把整机短信全部传给云端模型）；
     - **极高的网络往返与推理时延**（破坏 Magic Cue 毫秒级快捷胶囊的体验）。

## 2. 端侧数据是否需要做向量化？—— 第一性原理分析

### 2.1 结论：不对端侧所有数据进行全量向量化
在端侧千级数据规模下，性能瓶颈**不是“查找速度”**，而是**“关键事实精准度与领域语义对齐”**。

### 2.2 权衡对比矩阵

| 评估维度 | 全量端侧向量化 (Embedding + Vector DB) | 领域专用提取 + SQLite FTS5 倒排 + 词表扩展 | 决策结论 |
| :--- | :--- | :--- | :--- |
| **检索耗时** | 30ms ~ 100ms（含查询端侧 Embedding） | **< 3ms**（SQLite B-Tree / FTS5 内存检索） | 倒排索引速度远快于向量化 |
| **精确数字敏感度**<br>（金额、手机号、日期） | **极差**（数字在向量空间被平滑压缩，无法分辨 121.36 与 221.36） | **极佳**（精确提取 121.36 元，账期 8月1日-8月31日） | 账单与状态查询强依赖精确数字 |
| **端侧算力与电池消耗** | 持续在后台跑 Transformer 模型，发热且消耗电池 | **极低**（基于已有的 SQLite，零后台 CPU 唤醒） | 移动端必须杜绝无谓的电量消耗 |
| **语义对齐能力** | 仅做泛化相似度计算（“欠费”与“账单”文本相似度不一定高） | **领域规则驱动**（“电信账单应付金额 > 0”即判定为欠费待缴） | 业务逻辑推导胜过表面相似度 |
| **适用数据范围** | 适合**开放式非结构化长文本**（如长笔记、随手记、历史长对话） | 适合**强格式化、高确定性数据**（短信、日程、联系人、系统状态） | **分层治理，各司其职** |

## 3. 分层记忆与检索架构 (Hierarchical RAG)

```
+---------------------------------------------------------------------------------+
|                         Magic Cue 触发（双击 / 意图唤醒）                         |
+---------------------------------------------------------------------------------+
                                         │
                                         ▼
+---------------------------------------------------------------------------------+
| Phase 1: 轻量意图与领域路由器（Intent & Domain Router - < 10ms）                  |
| - 解析屏幕提问："手机是否欠费？"                                                  |
| - 提取意图：DOMAIN_TELECOM_BILL（话费 / 账单 / 欠费）                              |
| - 实体识别：target=当前用户，source_hints=['10000', '10086', '10010']           |
+----------------------------------------┬----------------------------------------+
                                         │
                                         ▼
+---------------------------------------------------------------------------------+
| Phase 2: 领域适配层快速提取（Domain Adapters - < 15ms）                           |
| ├─ 运营商短信适配器 (SmsStore):                                                  |
| │   SELECT * FROM sms_mms_info WHERE sender_number IN ('10000','10086','10010')  |
| │   ORDER BY start_time DESC LIMIT 3;                                           |
| │   解析出：电信 8月账单合计 121.36 元，实际应付 121.36 元                          |
| ├─ 用户画像与核心事实 (L0 Profile):                                              |
| │   常驻内存：用户主号为电信 181****6046                                        |
| └─ 日程/通讯录适配器 (若相关才激活)                                               |
+----------------------------------------┬----------------------------------------+
                                         │
                                         ▼
+---------------------------------------------------------------------------------+
| Phase 3: 上下文事实注入与单次生成（One-Shot Generation - ~1s）                     |
| 将精确提取的事实装配进 Prompt（消除多轮 Tool Calling 往返延时）：                  |
| <参考端侧事实>                                                                   |
| [短信/中国电信] 2026-09-08: 号码181****6046，8月账单合计121.36元，实际应付121.36元 |
| </参考端侧事实>                                                                  |
| 大模型直接输出胶囊：                                                              |
| {"cues":[{"kind":"bill","title":"电信账单","content":"8月账单应付121.36元"}]}     |
+---------------------------------------------------------------------------------+
```

### 3.1 记忆分层加载策略

- **L0：用户画像常驻卡片（User Profile Anchor - < 1KB，0ms）**
  - 常驻于内存，包括用户的主副手机号、常住地址、公司名称、常用联系人昵称映射（“老妈” -> “张某某”）。
  - 随任意 Magic Cue Prompt 一并附带，作为零耗时的常驻锚点。
- **L1：领域适配器与轻量全文检索（Domain Adapters & SQLite FTS5 - < 15ms）**
  - **短信库**：直读 `/data/app/el2/100/database/com.ohos.telephonydataability/rdb/sms_mms.db`；
  - **备忘录库**：直读 `/data/app/el2/100/database/com.huawei.hmos.notepad/rdb/notepad.db-dwr`；
  - **Bonio Memos**：读取 `~/.bonio/memos/`。
- **L2：长对话定期聚合摘要（Chat Session Digest）**
  - 对用户日常与 Bonio 的聊天对话，按会话或按天进行异步摘要，提炼成事实三元组（“用户喜欢喝美式”、“用户在准备考研”）沉淀进 User Profile，避免每次检索全量对话历史。
- **L3：充电触发增量向量化（Charging-Triggered Vectorization - 离线按需）**
  - 针对非结构化长笔记、长对话记忆，在特定时机做轻量级向量化支持模糊联想。

## 4. 充电触发增量向量化与摘要机制 (Charging-Triggered Scheduler)

### 4.1 为什么选择“充电即触发”（而非固定夜间）？
1. **快充普及度高**：现代主流手机普遍配备 66W~120W 超级快充，用户随时可能在办公室、车载、午休或碎片化时间充电；
2. **零续航顾虑**：只要接入电源（`chargingStatus === CHARGING`），CPU/NPU 计算就不再消耗电池电量，系统也不会对后台进程执行激进的省电降频策略；
3. **及时性更高**：无需等到凌晨 2 点，只要用户插上充电线 10~15 分钟，新产生的一批记忆与对话即可完成结构化摘要与向量化，拔掉充电线后立即享受最新索引效果。

### 4.2 调度器状态机与触发逻辑

```
   [设备运行中] 
        │
        │ 系统广播: commonEventManager.Support.COMMON_EVENT_CHARGING
        │ 或 batteryInfo.chargingStatus == ENABLE
        ▼
   [检测到充电连接] ──── 电池电量 > 15% ────┐
        │                                  │
        ▼ (满足条件)                        ▼ (电量过低不触发)
   [启动 ChargingVectorScheduler]       [延期等待]
        │
        ├─ 1. 扫描未生成摘要的对话与未索引的 Memos
        ├─ 2. 执行会话事实抽取（生成或更新 Profile Key-Value）
        ├─ 3. 增量计算文本嵌入向量（仅针对非结构化笔记）
        └─ 4. 写入本地轻量向量库（sqlite-vec / 索引文件）
        │
   [拔出充电器 / 充满电] ──── 立即安全中断并保存 Checkpoint ───► [恢复就绪状态]
```

## 5. 核心模块与接口设计

### 5.1 运营商短信解析器 (`dsh-plugins/bonio-bridge/src/sms_store.ts`)
- **数据源**：`/data/app/el2/100/database/com.ohos.telephonydataability/rdb/sms_mms.db`
- **解析能力**：
  - 发件人短号归一化：`10000`（中国电信）、`10086`（中国移动）、`10010`（中国联通）；
  - 正则模式提取：
    - 账单提醒：`账单合计(?:\s*)([\d\.]+)元`、`实际应付(?:\s*)([\d\.]+)元`
    - 话费余额：`当前余额(?:\s*)([\d\.-]+)元`、`欠费(?:\s*)([\d\.]+)元`
    - 账单周期：`账单周期为?([^\s，,。]+)`
  - 提供方法：
    - `getLatestTelecomBill(): Promise<TelecomBillInfo | null>`
    - `searchSms(query: string, limit?: number): Promise<SmsRecord[]>`

### 5.2 网关服务与 RPC 暴露 (`gateway.ts` & `driver.ts`)
- 注册 Local Tool：`sms_search`、`sms_bill`，支持 Agent 在 Ephemeral 会话中按需检索；
- 注册 Gateway RPC：`sms.bill`、`sms.search`，支持客户端在组织 Magic Cue 前快速预热拉取。

### 5.3 客户端 Magic Cue 控制器升级 (`MagicCueController.ets`)
- 胶囊类型扩展支持：`kind: 'bill' | 'contact' | 'calendar' | 'memo' | 'text'`；
- 意图预判与随路注入：在 `buildPrompt` 前，若检测到屏幕内容包含“话费/欠费/账单/停机”等关键词，先行从 `sms.bill` 拉取结构化事实注入 Prompt 的 `<参考端侧事实>` 标签内；
- 单次推理直出：大模型无需再通过 `bonio_node_invoke` 往返调用工具，直接基于注入的事实生成高准确度胶囊，端到端耗时大幅压低至 1 秒左右。

### 5.4 充电触发器 (`harmonyos/entry/src/main/ets/node/ChargingTriggeredScheduler.ets`)
- 监听 `@ohos.batteryInfo` 与公共事件；
- 在充电建立时通过 WebSocket RPC `memory.incremental_sync` 唤醒桥接服务处理增量索引。
